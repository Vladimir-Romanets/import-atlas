Technical Analysis: Duplicate Imports

This rule flags a file that pulls from the same target module through more than one import/export statement — a value import plus a separate type-only import, two re-export lines from the same file, or simply the same specifier written twice. It is computed once over the whole scanned graph, independent of the Tree tab's per-node 💡 hint, which only covers the pairs visible from wherever a tree node happens to sit.

Only statements that could actually be merged are counted. An import written inside a function — lazy(() => import('./Page')), a require() in a branch — is a deliberately separate way of reaching the module, so it is left out of the count even when the same file also imports that module statically. A require() or await import() at module scope is counted: it runs on load like any other import line.

1. Redundant Statements

Problem: Two or more statements doing the same job — naming the same source file — usually happened because the second import was added without noticing the first, or because a refactor left one behind.

Consequence: Readers scanning the top of the file see more import lines than there are actual dependencies, making the file's real surface area of dependencies harder to judge at a glance.

2. Common Legitimate Cause: Type-Only Imports

Problem: A value import (import { Button } from './Button') alongside a type-only import (import type { ButtonProps } from './Button') counts as two statements pulling from the same file.

Consequence: This is not a bug — it is valid, common TypeScript — but it can usually be written as one combined statement (import { Button, type ButtonProps } from './Button') without changing behavior.

3. Recommendations

Resolution Strategy: Combine the statements named in the row into one:

  • Two import statements: merge the named bindings into a single import { ... } from '...' line (adding type before an individual name, or importing them separately with one combined import and one combined import type, whichever the project's lint rules expect).
  • Two re-export lines: merge the forwarded names into a single export { ... } from '...' line.
  • Not this: do not fold a lazy import() into a static import line to clear a row — that would load the module eagerly and undo the code splitting. Rows like that are not reported in the first place, for exactly this reason.
