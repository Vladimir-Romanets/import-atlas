Potential Issues with Named Exports Duplicating an Imported Default

This rule flags modules that expose one and the same symbol twice — once by name and once as the default export — where every importer in the scan reaches it through the default. The duplication adds noise to the codebase and obscures the dependency graph.

1. Code Redundancy & Unused Exports

Problem: The module declares a named export alongside a default export of the same binding (export function Foo … export default Foo), but analysis shows that consumers strictly import the symbol via its default export.

Consequence: The named export exists solely as dead code in the module declaration, creating unnecessary API surface area and cluttering IDE auto-complete suggestions.

2. Public Interface Ambiguity

Problem: Providing multiple export mechanisms for the same underlying entity introduces inconsistency across the codebase.

Consequence: Developers working on different parts of the project may import the same utility differently (some using default imports, others using named imports), violating consistency and making global refactoring harder.

3. The Two Exports Are Not the Same Binding

Problem: export { Foo } exposes a live binding, while export default Foo exports the value Foo held at the moment the statement runs. The two look interchangeable but are not.

Consequence: If the module ever reassigns Foo after initialization, named importers observe the new value and default importers keep the old one — a divergence that is easy to introduce and hard to diagnose. Keeping a single export removes the hazard outright.

4. Before Removing the Named Export

Only the modules this scan walked count as consumers. A named export can still be imported by a test, a script, or a package consumer that no entry point reaches — and by anything the scan was told to skip with --exclude. Confirm the name is unused outside the graph before deleting it.

5. Recommendations

Resolution Strategy: It is recommended to keep only the export pattern that matches your project's established code style guidelines:

  • If your project style prefers Named Exports: Migrate all consuming files to use named imports (e.g., import { symbol } from './module') and drop the default export.
  • If your project style prefers Default Exports: Remove the unused named export from the module to keep the public interface clean and unambiguous.
