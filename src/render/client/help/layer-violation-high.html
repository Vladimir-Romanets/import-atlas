Technical Analysis: Layer Violations

This rule only runs when a layer-rules file applies: import-atlas.rules.json in --root, picked up on its own once it exists (generate a starting point with import-atlas init-rules), or a different file passed via --rules. It checks every import that crosses from one layer into another — a layer being the first folder under src/, or under the project root — against that file, and flags any crossing it does not allow.

Scored high on every row, unlike unimported-export findings: this is a deterministic check against a file the project's own team wrote, not a heuristic about what the import graph might be missing.

Unlike the circular-import and duplicate-import rules, a deferred import — lazy(() => import('./Page')), a require() inside a function — is still flagged here. Those other rules exclude deferred imports because they care about load order, which a lazy import cannot affect. This rule cares about architecture: a dynamic import still reaches into a layer it was not supposed to touch, whether or not it runs at module load.

1. Reading a Row

The first column is the layer the importing file belongs to; the second is that file's relative path. The third column is the specific violation: which layer it reached into, and through which file.

2. The Rules File

A layer-rules file is a JSON object mapping each layer name to what it may import from:

  • "*" — this layer may import from any other layer.
  • an array of layer names — an explicit allowlist of what this layer may import from.
  • a layer missing from the file entirely, or listed with [] — this layer may not import from any other layer.

Importing from a file in the same layer never counts as a violation, regardless of the rules.

3. Recommendations

Resolution Strategy:

  • Unintended crossing: move the dependency behind an interface the target layer already exposes to layers allowed to reach it, or relocate the importing code to a layer that is allowed to reach the target.
  • Intended crossing: add the target layer to the importing layer's allowlist in the rules file, and commit that change — the rules file is project policy, reviewed like any other config.
