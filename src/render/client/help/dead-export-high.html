Technical Analysis: Unimported Exports

This rule flags exported symbols (functions, variables, types, or classes) that no file in this scan imports. The import graph is the only evidence behind the claim, so read the caveats in section 4 before deleting anything.

1. Unnecessary Public API Surface

Problem: Exporting symbols that are only consumed locally within the defining file needlessly exposes them as part of the module's public interface.

Consequence: It clutters IDE auto-complete menus and creates a false impression that the symbol is a shared dependency across the application.

2. Dead Code Accumulation

Problem: Symbols that are neither imported externally nor called locally represent unused dead code.

Consequence: Unused code adds cognitive load during code reviews and carries maintenance overhead without offering any runtime value. It rarely costs bundle size — an unused named export of an ES module is normally tree-shaken away — so the cost lands on the people reading the source, not on the shipped output.

3. Misleading Static Analysis

Problem: Static analyzers and linters evaluate export keywords differently than internal declarations. ESLint's no-unused-vars, for instance, never reports an exported binding: as far as the rule is concerned, the module system is its consumer.

Consequence: An export keyword suppresses the one warning that would have told you the symbol is abandoned, leaving dead logic hidden in plain sight.

4. What the Import Graph Cannot See

Problem: This list is built from the modules the scan actually walked, starting at its entry points. A name can be alive for reasons no import edge records.

Check these before removing a symbol:

  • Public package API: if a library's index.ts was not passed as an entry point, every name it exports looks unimported here while real consumers live outside the repository. This is the single most common false positive.
  • Files outside the walk: tests, scripts, or apps that no entry point reaches are never read, so what they import cannot be credited. Files dropped by --exclude are omitted the same way, deliberately and without a warning.
  • Access the graph can't follow: names reached through a namespace import, require(), a dynamic import(), a DI container, or a string-keyed registry. (Where the scan detects such an import it credits the whole module, so those files are skipped entirely — but a lookup built at runtime leaves no edge at all.)

Consequence: Treat a row as a question to answer, not a verdict. If the viewer shows a coverage warning above the list, at least one importer went unread and the odds of a false positive rise accordingly.

5. Recommendations

Resolution Strategy: Refactor the symbol based on its actual usage and your project's code style requirements:

  • If the symbol is used only inside its own file: Remove the export keyword (convert it to a local const, function, or type) to keep the module's public interface clean and encapsulated.
  • If the symbol is completely unused: Delete the symbol declaration entirely to eliminate dead code.
  • If the name shown is default: the file has a default export nothing imports. Either drop export default and keep the declaration local, or remove the declaration altogether — whichever matches how the file uses it.
