Names Reached Through a Default Object

This is the least trustworthy group in the list. Each row is a name the file exports that also appears as a property of the object it default-exports — and that default export is imported elsewhere. Consumers most likely call it as Default.name(), an access the import graph cannot follow, so the name looks unimported when it is not.

1. Recommendations

Resolution Strategy: Verify before removing anything. Unlike the other groups, the default assumption here is that the symbol is alive.

  • To confirm the name is used: search the codebase for property access on the default import (Utils.name, Utils['name']) rather than for the bare identifier. An IDE's "Find Usages" on the property is more reliable than a text search for the name alone.
  • If it is used through the object: nothing is wrong with the symbol. The finding is a limitation of static import analysis — dismiss it, or take it as an argument for the refactor below.
  • If nothing reaches it, through the object or otherwise: it is genuinely dead and can be removed — from both the declaration and the aggregate object.
  • To stop the ambiguity at the source: replace the default object with named exports. Every reason below is an argument for doing so, and it makes future findings in this file trustworthy instead of speculative.

2. Runtime Errors Due to Accidental Code Removal

Problem: Static analysis tools and linters (e.g. ESLint) cannot reliably trace property access on default objects (such as defaultImport.methodName()). To these tools — and to this one — the underlying symbol appears to be unused.

Consequence: A developer or an automated cleanup tool might remove the "unused" function from the source file. The project still compiles, but fails at runtime for end users with a TypeError: defaultObject.method is not a function. This is exactly the mistake section 1 is guarding against.

3. Weakened Tree Shaking

Bundlers (such as Webpack, Vite, and Rollup) rely on the static analysis of ES modules.

Problem: An exported object is a single value, so dead-code elimination has to reason about its properties instead of about module-level bindings — a much weaker analysis.

Consequence: Unused members frequently survive into the bundle even when only one of them is called. Rollup can drop unreferenced properties of a plain object literal in favourable cases, and other bundlers manage it inconsistently, but none of it is as dependable as the per-export elimination named exports get for free.

4. Degraded Auto-Imports & Developer Experience

Problem: IDE auto-import (VS Code, WebStorm) indexes exported names.

Consequence:

  • Typing a member's name offers no auto-import: only the default export itself is suggested, and only under the name the importing file chooses for it.
  • Code navigation (Ctrl+Click / Cmd+Click) on a member lands on the property in the object literal, which may be a shorthand reference rather than the implementation.

5. Less Reliable Symbol Traversal

Problem: The name no longer crosses the module boundary as a name.

Consequence:

  • Dependency tooling that works on import edges — including this viewer — cannot attribute the usage to the symbol.
  • "Find Usages" and Rename Symbol still work in TypeScript as long as the object's type is inferred and flows to the call site intact. They degrade in plain JavaScript, and in TypeScript wherever the object passes through any, an index signature, or a dynamic key.

6. Circular Dependency Hazards

Problem: A default-exported object is built by an assignment that runs when the module body executes. Function declarations, which named exports commonly are, are hoisted before any module body runs.

Consequence: In a cycle between Module A and Module B, an importer that runs first may observe the object as undefined or only partly initialized, while a hoisted named function would have been callable. The cycle is the root cause, but the object export is what turns it into a crash at startup.

Comparison Summary

Criterion Default Object Export Named Exports
Tree Shaking ❌ Unreliable (unused members often kept) ✅ Predictable per export
Refactoring Safety ❌ Low (risk of runtime errors) ✅ High
IDE Auto-Imports ❌ Not offered per member ✅ Supported out-of-the-box
Import-Graph Analysis ❌ Blind to member usage ✅ Accurate
