Technical Analysis: Circular Imports

This rule flags files that import each other in a loop, computed once over the whole scanned graph (every file the walk reached, not just the ones under a given entry point). Each row is one loop — a real chain of imports that closes back on the file it started from, visiting no file twice. The count in the left-hand column is how many files are on that loop, so it matches the number of names in the path beside it. The one row that is not a loop is self-import, a file that reaches itself in a single step.

Loops of four files or fewer are listed, since a longer one is rarely a distinct problem — usually it is two shorter ones chained together, and fixing either shortens it. Raise that with --max-cycle-length to see wider loops, or drop it to 2 for mutual imports only. A group holding no loop that short is still reported — see below.

Only imports that run while a module is evaluating are counted. An import written inside a function — lazy(() => import('./Page')), a require() in a branch — runs on call, long after every module in the loop has finished loading, so a loop that closes only through one of those is not reported. The dependency is real and still drawn in the Tree tab; what is absent is the load-order coupling this rule is about. A require() or await import() at module scope is counted — those block evaluation exactly like a plain import.

1. Not the Same as the Tree's ⚠ Warning

Difference: The Tree tab marks a node ⚠ circular import the first time a depth-first walk from one entry point revisits a file still open on its current path. That catches only the loops (and only the first back-edge) visible from wherever you happened to click. This list is computed from the graph itself, so it depends on neither an entry point nor a walk order — nor on where you clicked.

Consequence: A loop can appear here without ever showing a warning on the tree, if no entry point's walk order happens to hit its back-edge. The reverse does not hold as neatly: a warned file is certainly caught up in circular imports, but the particular loop the tree stumbled into may be longer than the ones printed here, so it need not appear as a row of its own.

2. Fragile Load Order & Partial Modules

Problem: When module A imports module B and B imports A (directly, or through a chain of other files), one of them is still mid-evaluation when the other reads from it.

Consequence: Depending on which file loads first, a binding pulled from the still-evaluating module can be undefined — a bug that reproduces only under specific import orders, making it disproportionately hard to track down compared to how it was introduced.

3. Bundler & Tree-Shaking Friction

Problem: Bundlers have to break cycles at build time by choosing an evaluation order, and can't always prove a cycle is side-effect-free.

Consequence: Code inside a cycle is more likely to be bundled together and evaluated eagerly, even when only a small piece of it is actually used, working against tree shaking.

4. Reading the Rows

Problem: The path column reads like a.ts → b.ts → c.ts → a.ts — each arrow is a real import edge in the scan, and the chain closes back on its starting file. Breaking any one of those arrows removes that loop.

  • Several rows can share files. Files often tangle into a group where everyone reaches everyone, and such a group holds many loops. Each gets its own row, and the hover text says how large the group is and how many loops were found in it. An import that keeps reappearing across rows is worth looking at first: the more loops run through it, the more of them one change closes.
  • Very tangled groups are capped. No single group prints more than 100 rows. When there are more, the shortest ones are kept and the hover text says how many were found in total, so the number is never quietly lost.
  • Shortest first. Two-file rows head the list: a pair importing each other is both the easiest to understand and usually the easiest to separate.
  • A group with no short loop — a long ring of files, say — still gets exactly one row, carrying the shortest cycle through its alphabetically first file. The hover text says so, so a group is never silently skipped for being awkwardly shaped.

5. Recommendations

Resolution Strategy: Pick whichever keeps the direction of the dependency honest:

  • Extract the shared piece: if both files need something from each other, move that shared code (a type, a constant, a small utility) into a third module both sides import from, so the dependency only flows one way.
  • Break one direction: if one side's dependency on the other is incidental (used in one rarely-hit branch, say), move the import inside the function that needs it — const { helper } = await import('./helper') — so it runs on call rather than on load. That clears the row: an import inside a function is no longer part of the evaluation loop. Moving the call but leaving it at module scope does not.
  • Self-import: a file that imports itself, directly or through a re-export chain, usually means a barrel re-exports something the file underneath it also pulls back in — import directly from the underlying file instead of through the barrel.
